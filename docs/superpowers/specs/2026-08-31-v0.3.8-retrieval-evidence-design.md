# dsh-knowledge 0.3.8 retrieval and evidence-chain design

## Goal

Version 0.3.8 makes proactive retrieval low-latency and deterministic, gives every search hit an ordered and bounded evidence window, and lets the model continue reading directly from the hit anchor. It is an additive compatibility release: existing `autoRetrieve`, `SearchHit.text`, `siblingContext`, pagination calls, stored chunks, and 0.3.7 data remain usable.

This release does not change ordinary chunking, persist bridge text, migrate the database, rebuild embeddings, or address mixed embedding spaces and semantic-chunk centroid correctness. Those require separate follow-up designs.

## Retrieval execution

`KnowledgeService.search(request, execution?)` accepts an internal execution policy with a rerank mode and abort signal. Normal callers retain configured reranking. Proactive retrieval explicitly skips service-level reranking, then may invoke a remote reranker once under the remaining part of a four-second total deadline. It never starts a local reranker. Remote retries share one total deadline; proactive retrieval uses zero retries. An external abort stops without logging, injection, or state mutation.

The proactive query planner always preserves the current message within a 200-character head/tail budget. It adds a second, history-aware query only for short or deictic follow-ups, searches the two variants independently, and fuses them with reciprocal-rank fusion. Seen evidence is removed before reranking and per-base seat allocation. A same-topic turn may add one fresh evidence item during the five-minute window; a new topic may add three. State is committed only after the background is folded or injected.

Explicit references to a disabled or weight-zero base do not fall through to other bases. Pure identifiers use a strict exact-match lane. Short-query LIKE scores are normalized as `1024 / (1024 + searchTextLength)`. An empty metadata allow-list matches no documents in both service and storage layers.

## Evidence windows

Each new search hit carries an optional additive `contextWindow` with ordered `before`, `anchor`, and `after` excerpts. Excerpts retain their chunk id, index, heading, chunk-relative character range, and truncation flags. The window reports its anchor, estimated token count, and whether more content exists on either side. `SearchHit.text` remains the complete canonical anchor. `siblingContext` remains populated and deprecated throughout 0.3.x, but new model-facing paths do not consume it.

A shared ContextComposer batch-loads merged index ranges, composes windows without crossing heading paths by default, and serializes the same representation for reranking, explicit search, proactive previews, and evaluation. The anchor receives budget first. Oversized anchors are clipped around the strongest query match at sentence boundaries. Neighbours are added nearest-first. Exact suffix/prefix overlap of at least 24 characters is removed without deleting anchor evidence.

The fixed internal profiles are:

- rerank: 128 query tokens, 352 evidence tokens, 480 pair tokens;
- explicit search: 768 tokens per hit and 8192 tokens per rendered result;
- proactive preview: 180 tokens per hit and 640 tokens for the complete background;
- anchored read: 1600 tokens by default, configurable from 128 to 4096 per call.

Single- and multi-query retrieval use one rerank implementation and stable tie ordering. A rerank failure preserves retrieval order and still returns valid evidence windows.

## Tool contract

Search source labels expose `chunkIndex` and one continuation hint. `knowledge_get_document` keeps its current page mode but uses true SQL limit/offset. Supplying exactly one of `anchorChunkId` or `anchorIndex` selects context mode; page and context parameters cannot be mixed. Context mode accepts before/after radii from 0 to 10, a 128–4096 token budget, an optional 500-character focus, and an explicit cross-heading switch. It returns `readMode: "context"` and a context window. Invalid, stale, disabled, or document-mismatched anchors fail explicitly.

Grep rendering exposes each match's character offsets and a direct continuation instruction for `knowledge_read_document`.

## Quality and release

Deterministic tests cover real SQLite proactive retrieval, rerank invocation counts, total deadlines and aborts, short CJK queries, history retention, fresh evidence, identifiers, ordered windows, heading boundaries, overlap removal, budgets, batching, rerank parity, anchored reads, visible offsets, empty filters, and 0.3.7 compatibility.

Benchmark schema v2 evaluates the exact model-visible search render and proactive background. Existing 40-question retrieval metrics remain perfect; visible-evidence recall and one-call bridge success must be 1.0, with zero ordering and budget violations. Duplicate ratio, tool-call count, and latency remain report-only for this release.

After typecheck, tests, benchmark, build, package verification, packed smoke, and local-rerank smoke pass, the package is bumped to 0.3.8 and pushed to GitHub. The `v0.3.8` tag is pushed only after GitHub Actions is green. npm publication is explicitly excluded.
