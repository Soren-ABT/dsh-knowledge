# dsh-knowledge v0.3.9 Release Design

## Objective

Publish the community integration from PR #14 as dsh-knowledge v0.3.9 while
preserving contributor attribution and keeping the npm publication under the
maintainer's direct control.

The release is additive and backward-compatible. It does not introduce a
database migration, force an index rebuild, change embedding models, or alter
the v0.3.8 retrieval and evidence-window contracts.

## Release contents

The release documentation will describe the following user-visible changes:

- import a single local file or a directory tree by absolute path;
- retain explicit source identity so a top-level source can be repointed and
  reindexed from its new location;
- isolate raw-source storage when separate directory roots contain the same
  relative file path;
- preserve the previous committed raw copy if a replacement reindex fails;
- report per-file failures from partial directory imports;
- default an empty Ollama embedding base URL to
  `http://127.0.0.1:11434` without changing OpenAI-compatible validation;
- add the related Chinese and English localization strings;
- improve theme tokens, toast dismissal, nested/root popover placement, and
  explicit model-selection behavior.

ThinkForge-core will be credited in the release notes for the original
contributions integrated through PRs #10–#13. Maintainer regression tests and
hardening remain identifiable as separate commits in the merged history.

## Versioned files

The implementation updates:

- `package.json` to version `0.3.9`;
- `dsh.plugin.json` to version `0.3.9`;
- `CHANGELOG.md` with a new first release section dated 2026-09-02;
- `docs/releases/v0.3.9.md` with the copy used for the GitHub Release;
- README installation examples and the current-release overview where they
  explicitly name v0.3.8.

The pnpm lockfile has no root package-version field and will not be rewritten
unless a release edit genuinely changes its resolved content.

## Validation gates

Before the release commit is pushed, the workspace must pass:

1. `npm run release:check`, including build policy, release metadata,
   production audit policy, typecheck, all Vitest tests, retrieval benchmark
   v2, build, package verification, and clean-tree enforcement;
2. the focused Windows local-path import/source-tracking test group;
3. an explicit `npm pack --dry-run` or equivalent tarball inspection showing
   version 0.3.9 and the required runtime/release files;
4. a final clean working-tree and version-consistency check.

After the release commit reaches GitHub, all required CI jobs must be green:
Node 22/24 Quality, Windows/Linux/macOS Native, and Windows/Linux packed DSH
smoke. The manually triggered local-rerank smoke may remain skipped because
v0.3.9 does not change the rerank runtime.

## Publication sequence

1. Create one release-preparation commit on `main` and push it.
2. Wait for all required CI jobs on that exact commit to pass. Fix real
   failures on `main`, rerun the complete local gate, and wait for the updated
   commit if necessary.
3. Create the annotated tag `v0.3.9` at the verified commit and push the tag.
4. Prepare a GitHub Release draft from `docs/releases/v0.3.9.md`; do not
   publish the release yet.
5. Provide the verified npm publication command and tarball metadata to the
   maintainer. The maintainer runs `npm publish` personally.
6. Verify that `npm view dsh-knowledge version` reports `0.3.9`.
7. Only after registry verification, publish the prepared GitHub Release.

## Failure handling

- Do not create or push the tag while required CI is failing or pending.
- Do not execute `npm publish` from the agent.
- Do not publish the GitHub Release while npm still reports an older version.
- Never retry an ambiguous npm publication automatically; verify registry
  state first.
- If a release-preparation defect is found before tagging, fix it normally and
  rerun all gates. If a defect is found after tagging but before npm publish,
  stop and ask the maintainer before changing the published tag.
- Keep the integration branch and contributor branches intact.

## Acceptance criteria

- `package.json`, `dsh.plugin.json`, CHANGELOG, release notes, README examples,
  npm tarball metadata, and `v0.3.9` all identify the same version.
- The release commit is present on local `main`, `origin/main`, and GitHub.
- All required CI checks pass for the tagged commit.
- The Git tag is annotated and points to the verified release commit.
- The GitHub Release remains a draft until npm 0.3.9 is visible publicly.
- Contributor attribution is present in the release notes and commit history.
- No npm publication is performed by the agent.
